# AI 扩展规划

## 1. 规划目标

`robot-ops-dashboard` 后续会预留 AI 扩展能力，但 AI 在本仓库中的角色应当是“辅助观察和诊断”，而不是“独立完整 AI 平台”。

本阶段重点是定义扩展方向和接入方式。

## 2. 三条主要扩展方向

## 2.1 机器学习异常分类

目标：

- 对历史任务、设备状态、通信波动和测试结果进行异常分类

可能输入：

- 任务超时特征
- 电池波动
- 网络抖动
- 设备故障标签
- 测试失败统计

可能输出：

- 异常类型
- 风险等级
- 置信度
- 推荐排查方向

## 2.2 LLM 诊断建议

目标：

- 根据任务状态、设备状态、告警上下文和日志摘要生成可读诊断建议

适合承载的输出：

- 问题摘要
- 初步原因推测
- 推荐排查步骤
- 需要人工确认的风险点

设计原则：

- LLM 输出必须与证据分离展示
- LLM 输出必须可回溯上下文
- LLM 输出属于建议，不应被误解为控制命令

## 2.3 YOLO 视觉检测结果展示

目标：

- 展示来自相机或巡检流程的目标检测结果

适合展示的内容：

- 检测框结果
- 检测类别
- 置信度
- 对应截图或视频片段
- 与任务或告警的关联关系

## 3. 建议的数据接入方式

AI 能力不应直接耦合到页面逻辑中，建议通过统一输入对象接入。

推荐方式：

- 机器学习结果通过 HTTP 接口或离线结果文件导入
- LLM 建议通过后端服务生成后写入统一对象
- YOLO 结果通过推理服务输出结构化结果和证据链接

## 4. AI 对 Dashboard 的价值

AI 的价值不在于替代运维或测试工程师，而在于：

- 缩短异常定位时间
- 提前聚焦高风险问题
- 帮助形成更易读的排障建议
- 提供图像或日志层面的辅助证据

## 5. 风险与约束

需要明确以下限制：

- 本仓库不承担完整 AI 训练平台职责
- 本仓库不承担模型部署平台职责
- AI 输出不能直接驱动底层控制行为
- AI 输出需要保留置信度与人工确认环节

## 6. 推荐演进顺序

建议按以下顺序推进：

1. 先接入结构化告警与任务上下文
2. 再接入基于规则或统计的异常分类
3. 再引入 LLM 诊断建议
4. 最后叠加 YOLO 视觉证据展示

这样可以避免一开始就把 AI 部分做成黑盒，也更适合项目演进与对外说明。
