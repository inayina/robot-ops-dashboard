# 总体设计

## 1. 设计目标

`robot-ops-dashboard` 的目标不是替代单个机器人子系统，而是在多个系统之上提供统一的运维与测试观察层。

核心目标：

- 聚合 AMR 任务流、设备状态、测试结果与告警信息
- 给运维、测试和研发提供统一的状态入口
- 用统一的数据模型屏蔽上游接口差异
- 为后续 AI 能力扩展预留清晰挂载点

## 2. 目标用户

- 机器人运维工程师：关注任务阻塞、机器人在线状态、异常聚合
- 测试验证工程师：关注批量测试执行情况、失败原因、回归稳定性
- 研发工程师：关注链路状态、设备通信、接口映射与问题定位
- 项目负责人：关注交付状态、风险分布和系统健康概览

## 3. 系统定位

本仓库对应的是“上层 Dashboard 与数据聚合设计层”。

建议的系统分层如下：

1. 上游业务/控制系统层
   - `amr_warehouse_navigation`
   - `ros2-robot-digital-twin`
   - WMS / 测试脚本 / 设备网关 / AI 推理服务
2. 数据适配与归一化层
   - HTTP 拉取适配器
   - Mock WMS task creation HTTP proxy
   - MQTT 订阅适配器
   - micro-ROS 状态桥接器
   - 统一数据模型映射器
3. Dashboard 服务层
   - 任务视图数据
   - 设备视图数据
   - 告警视图数据
   - 测试视图数据
   - AI 诊断结果视图数据
4. 展示层
   - 运维总览页
   - 任务页
   - 设备页
   - 告警页
   - 测试页
   - AI 扩展页

## 4. V0.1 设计原则

V0.1 采用“先定义，再实现”的策略：

- 先沉淀文档、页面、数据模型与 Mock 数据
- 先围绕 `amr_warehouse_navigation` 的 Mock WMS HTTP API 建模
- 先把观测链路设计清楚；交互能力必须保持小范围、显式、可验证
- 先统一术语和字段，再实现代码和前端

## 5. 数据域划分

当前建议将数据分成五个核心域：

### 5.1 AMR 任务域

用于承接 WMS 或调度系统输出的任务生命周期数据，例如：

- 待分配
- 已分配
- 执行中
- 阻塞
- 已完成
- 失败

### 5.2 设备状态域

用于承接机器人下位机、传感器和通信模块状态，例如：

- 电池状态
- 底盘控制器在线状态
- 激光雷达状态
- 安全控制器状态
- MCU / micro-ROS 节点存活情况

### 5.3 告警域

用于聚合系统异常、任务异常、设备异常和测试异常。

示例：

- 任务超时
- 电量过低
- 设备离线
- 通信抖动
- 视觉检测异常

### 5.4 测试验证域

用于记录测试批次、场景结果与回归状态。

### 5.5 AI 洞察域

用于后续承接：

- 机器学习异常分类结果
- LLM 诊断建议
- YOLO 视觉检测结果

## 6. 仓库边界

本仓库关注“看板、汇总、洞察”，不直接承担控制职责。

明确边界如下：

- 不直接控制 Nav2
- 不直接控制电机或下位机
- 不通过 MQTT 下发任务或控制指令
- 仅提供最小 Mock WMS task creation HTTP proxy，不替代完整 WMS
- 不替代完整 AI 训练、部署与运维平台

本仓库可以展示来自这些系统的数据，但不直接成为它们的控制平面。

## 7. 建议的后续实现架构

在进入代码实现阶段时，可以按以下方向推进：

1. 先实现数据接入层和最小 Mock WMS task proxy
2. 再实现统一数据模型与 API
3. 再实现 Dashboard 页面
4. 最后叠加告警规则和 AI 扩展

这样可以把复杂度控制在可演进的范围内，避免一开始就把仓库做成“大而全平台”。
